# ExecPlan: Production Story Studio Demo Completion

This plan follows `.agent/PLANS.md`. It is the living execution plan for turning the current
`pocketfm-contest-forge` demo into a production-quality public demo with live story artifacts, no
creative heuristic fallback, and no hidden fixture output in the main user path.

## Purpose / Big Picture

The app currently has a public SvelteKit MVP with one proven live Grok path for `cold-open-lab`,
but the main page still surrounds that live result with a deterministic fixture/demo forge plan.
That means a viewer can see heuristic scores, fixture pilot beats, static AI council prompts, and
demo module summaries beside the real live panel. The goal of this plan is to finish the demo the
right way: every serious story artifact shown in production is either generated by live AI, rejected
by a visible quality gate, or shown as locked/unavailable. The production UI must not use
deterministic prose as a substitute for failed AI.

Success is observable when `https://pocketfm-contest-forge.vercel.app` loads the Serial Story Studio
interface, accepts a story seed and access code, runs the live Grok-backed studio flow, and displays
typed artifacts for cold opens, debt ledger, cliffhanger futures, trope mutations, and council
review with provenance, prompt versions, quality-gate outcomes, and clear failure states. If the
provider key is missing, the access code is wrong, the model times out, JSON is invalid, schema
validation fails, or prose quality is rejected, the UI preserves the seed and shows the failed or
locked state. It must not display heuristic or fixture prose as a replacement.

## Surprises & Discoveries

The production Grok path is healthier than the surrounding product surface. `runLiveColdOpen` is
server-side, gated by `STORY_AI_ACCESS_CODE`, rate-limited, and backed by a provider adapter that
fails closed. The larger debt is that `src/routes/+page.svelte` imports `createDefaultForge()` and
computes the main plan in the browser, so deterministic fixture output is still the dominant first
screen.

`ForgeContestStory.forge(request, 'live')` already refuses to substitute deterministic output and
returns `AI_PROVIDER_UNAVAILABLE`. Keep that fail-closed behavior. Do not try to make the old forge
use case half-live by mixing live and deterministic sections.

`LiveModuleExecutor` is intentionally conservative: it supports only modules with configured
module-specific quality gates. The default registry now covers `cold-open-lab`, `binge-debt-ledger`,
and `cliffhanger-futures`; other modules stay blocked until their gates exist. Keep that posture.
Broadly enabling all registered modules would create the exact technical debt this plan is meant to
avoid.

The current AI council is not live AI. It is a static prompt runbook embedded in
`ForgeContestStory`. In production it should be either hidden as a developer runbook or replaced by
a provider-backed council artifact with schema validation and prose review.

After consolidation, `/Users/hbpheonix/pocketfm` is the canonical local repo. The older nested path
under `/Users/hbpheonix/fairytaleswithspice` no longer exists as the active app checkout.

The first production Story Studio boundary can be implemented before the route is rebuilt. This
keeps contract and application behavior testable while the current UI still renders the old
fixture-demo forge plan.

Live-module enablement now depends on `LiveModuleQualityGateRegistry`, not a broad set of supported
IDs. Each module must provide its own review builder before the executor will call the provider.

`binge-debt-ledger` can run live after `cold-open-lab` succeeds. Because the old deterministic pilot
cannot be used in production, its live input is built from accepted cold-open variants, seed story
state, and existing secrets. Direct `module.run(..., live)` still fails closed; provider-backed live
execution goes through `LiveModuleExecutor`.

`cliffhanger-futures` can run live after accepted cold-open and binge debt artifacts exist. Its live
input is assembled from accepted cold-open variants plus accepted open/stale debt labels instead of
the deterministic pilot episode. This keeps the production chain honest while still giving the
module the episode-beat and unresolved-debt shapes its contract expects.

Definitions:

"Fixture/demo" means deterministic local output used for tests, development, and explicitly labeled
preview screens. It can be useful but must not be presented as production AI advice.

"Live AI" means provider-backed generation through `StoryModuleProvider`, `LiveModuleExecutor`,
module-owned schemas, and prose quality checks. Live AI can succeed, fail, or be rejected. It must
not silently return fixture output.

"Story artifact" means a typed result a writer can use: a cold open variant, debt ledger, future
cliffhanger path, trope mutation, or council review. Artifacts need status, provenance, issues, and
tracking events.

"Fail closed" means preserve user input and return a visible failure or locked state instead of
inventing replacement prose locally.

## Plan of Work

First, add a production story-studio contract. Create
`src/lib/core/contracts/storyStudioContract.ts` and tests beside it. This contract is the production
surface for the route and should not reuse `ForgePlan` fields that are inherently heuristic. Export
these names:

- `StoryStudioMode = 'production' | 'fixture-demo'`
- `StoryStudioArtifactId = 'cold-open-lab' | 'binge-debt-ledger' | 'cliffhanger-futures' |
'trope-mutation-lab' | 'council-review'`
- `StoryStudioArtifactStatus = 'locked' | 'running' | 'accepted' | 'rejected' | 'failed' | 'stale'`
- `StoryStudioArtifact`, containing `id`, `label`, `status`, `summary`, `result`, `issues`,
  `provenance`, and `nextAction`
- `StoryStudioRun`, containing `generationMode: 'live-ai'`, `brief`, `requestedAt`, `artifacts`,
  `qualitySummary`, `contestFreshness`, and `trackingEvents`
- `StoryStudioResponse`, a success/failure union with error codes `ACCESS_DENIED`,
  `ACCESS_NOT_CONFIGURED`, `RATE_LIMITED`, `CONTRACT_INVALID`, `CONTEST_NOT_FOUND`,
  `PROVIDER_UNAVAILABLE`, and `STUDIO_RUN_FAILED`

Second, create `src/lib/application/runLiveStoryStudio.ts`. This use case receives a
`ForgeRequest`, `ContestResearchPort`, `StoryModuleProvider`, `StoryModuleRegistry`, and clock. It
validates the request, resolves the contest brief, builds story state, runs live-capable artifacts in
an explicit order, and returns `StoryStudioResponse`. The first order is:

1. `cold-open-lab`
2. `binge-debt-ledger`
3. `cliffhanger-futures`
4. `trope-mutation-lab`
5. `council-review`

If an earlier module fails, continue only when the later module can honestly run from the seed,
brief, and story state without pretending the failed artifact exists. Otherwise return a locked
artifact with `nextAction` explaining which accepted artifact is required.

Third, extract duplicated module input assembly from `ForgeContestStory` into
`src/lib/application/storyModuleInputs.ts`. This file should export named builders for each module:
`buildColdOpenLabInput`, `buildBingeDebtLedgerInput`, `buildCliffhangerFuturesInput`,
`buildTropeMutationLabInput`, and later `buildCouncilReviewInput`. `ForgeContestStory` may use the
same builders for fixture/demo mode so the contract shape stays aligned.

Fourth, generalize `LiveModuleExecutor` without weakening it. Replace the broad
`supportedModuleIds` set with a module-specific gate registry, for example
`LiveModuleQualityGateRegistry`, where each supported module ID maps to an output-to-prose-review
adapter and acceptance rule. If a module has no configured gate, live execution must still fail with
`INVALID_INPUT` and no provider call. Keep one JSON repair attempt. Keep provider adapters as
transport only.

Fifth, make `binge-debt-ledger` live-capable. Update its `prompts.ts` so the model returns only the
module-owned JSON schema. Add tests for valid output, provider unavailable, timeout, fenced JSON
repair, unrecoverable malformed JSON, schema rejection, and prose quality rejection. The quality
gate must require concrete promises, open/paid/stale status, payoff windows, and at least one
relationship or status cost.

Sixth, make `cliffhanger-futures` live-capable. Its prompt and quality gate must reject fake
cliffhangers that only hide information without a payoff path. Accepted output must include the
listener question, the next episode pull, the planned payoff movement, and the risk of frustrating
the audience.

Seventh, make `trope-mutation-lab` live-capable. Its prompt and quality gate must require the
familiar trope, the mutation, why the mutation still satisfies the contest lane, how it creates a
repeatable serial engine, and one concrete scene proof. It should allow trope inversion and
subversion, but reject abstract genre commentary that gives no playable story move.

## Idempotence and Recovery

Each phase should be independently revertible. Keep contract, orchestration, each live module,
council review, UI rebuild, and deployment proof in separate PRs unless a small follow-up fix is
needed for review.

If a baseline command fails before edits, stop and record the failure in `Progress` and
`Surprises & Discoveries`. Do not start implementing on top of an unexplained broken baseline.

If xAI credentials are missing locally, use fake-provider unit tests and no-key server tests. Do not
mock production success in the deployed smoke. The deployed smoke either proves the real provider
path or remains incomplete.

If Grok output is weak, malformed, or too slow, improve prompts, schemas, timeout handling, or
quality gates. Do not lower the quality bar or backfill with deterministic prose.

If a module cannot honestly run because a prerequisite artifact failed, return a locked artifact
with a clear `nextAction`. Do not fabricate prerequisite output.

If Vercel preview authentication blocks live smoke, record that in `docs/TRACKING.md` and use
post-merge production smoke only when the app is intentionally public.
