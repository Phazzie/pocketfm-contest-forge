# ExecPlan: Public Hosted Grok MVP

This plan follows `.agent/PLANS.md`. It is the living plan for taking
`pocketfm-contest-forge` from local fixture-demo prototype to a public Vercel-hosted MVP that can be
shown to family with real AI output and minimal technical debt.

## Purpose / Big Picture

The MVP is a public hosted writing lab where a user enters a Pocket FM-style story seed and receives
one high-quality, schema-validated, provenance-tracked AI result from `cold-open-lab`. The result
must be generated by Grok 4.20 multi-agent reasoning through a server-side provider adapter, not by
fixture/demo output or browser-side API calls.

Success is observable when a public Vercel URL loads the app, accepts a story seed, calls the
server-side Grok provider for `cold-open-lab`, rejects weak or invalid output, and displays accepted
AI output with provider/model/prompt metadata. The repo must use PRs, CI, quality gates, and branch
protection so future work cannot silently add type escapes, fallback prose, or broken builds.

## Plan of Work

First, merge the quality-enforcement branch. This branch must establish CI, Node 22 pinning, strict
TypeScript options, explicit `any` budget, documented eslint-disable rationale, and PR-ready
verification. After merge, enable branch protection on `main` requiring CI.

Second, add Vercel deployment support on a separate PR. Replace ambiguous `adapter-auto` with
explicit Vercel support, keep server-side secrets server-only, and verify a Vercel preview
deployment before merging. Do not add live AI in the same PR.

Third, execute `docs/NEXT_AUTONOMOUS_EXECUTION_PLAN.md`: add the provider port, fake-provider live
executor, `cold-open-lab` prompt assembly, JSON repair, schema validation, and deterministic prose
quality gate. Merge only after fake-provider success and failure tests pass.

Fourth, add the Grok adapter behind the provider port. Use server-only code and env validation:
`XAI_API_KEY`, `STORY_AI_PROVIDER=xai`, `STORY_AI_MODEL=grok-4.20-multi-agent`, and
`STORY_AI_REASONING_EFFORT=medium` by default. Use `high` only for a separate critique/selection
step after the generation path is stable.

Fifth, add the public-demo gate and cost controls. A public Vercel app must not allow unlimited
anonymous paid model calls. For MVP, use one server-side access code and a small per-process/IP
rate limiter. This is not permanent auth; it is abuse control for a public family/demo URL.

Sixth, add the MVP UI states. The UI must distinguish fixture-demo, live loading, live success, live
failure, schema rejection, prose rejection, and provider unavailable. It must preserve the user's
seed and never overwrite accepted writer decisions silently.

Seventh, ship production. Merge PRs only after CI and preview deployments pass, then promote/main
deploy to Vercel production. Final verification must include one real Grok run from the public URL
and one intentional failure path without exposing secrets.

Remote gates:

- GitHub Actions CI passes on every PR.
- Vercel preview deployment succeeds on every app-impacting PR.
- `main` is protected and requires CI before merge.

MVP acceptance:

- Public Vercel production URL loads successfully.
- A user can submit a story seed and receive one accepted Grok-generated `cold-open-lab` result.
- The result includes provider, model, reasoning effort, prompt version, module version, latency,
  status, issues, and tracking events.
- Weak AI output is rejected with visible prose/schema issues instead of hidden rewriting.
- No live path returns fixture, deterministic, or heuristic prose as a substitute for failed AI.
- The browser never receives `XAI_API_KEY`.
- The app has basic public-demo abuse control before paid AI calls.
- Review comments on all MVP PRs are addressed before merge.

## Idempotence and Recovery

Every PR should be independently revertible. Keep provider boundary, Vercel setup, Grok adapter,
and public UI work in separate PRs so a failure in one layer does not force a broad rollback.

If Vercel setup fails, keep local CI green and record the Vercel error in `docs/TRACKING.md`.
If Grok output is malformed or weak, fail closed and record the rejection; do not patch around it
with deterministic prose.

If cost or abuse risk appears before public launch, disable live calls behind the access gate and
ship fixture-demo publicly only as a temporary preview, not as the MVP.

## Interfaces and Dependencies

Provider/env defaults:

- `XAI_API_KEY`: required only for server-side Grok calls.
- `STORY_AI_PROVIDER=xai`
- `STORY_AI_MODEL=grok-4.20-multi-agent`
- `STORY_AI_REASONING_EFFORT=medium`
- `STORY_AI_ACCESS_CODE`: required for public demo live calls.

Do not expose provider credentials to `src/routes/+page.svelte` or any client bundle. Provider
calls must run in server-side route/load/action code or server-only application services.
